Проблемная сеть

CLIENT_IP=178.178.242.236

Это публичный IPv4 сети/устройства, с которого пользователь прямо сейчас будет выполнять тест.

Цель

Определить, доходит ли трафик от 178.178.242.236 до VPS 206.245.129.65 и чем отличается поведение:

1. AmneziaWG — UDP 32296
2. SSH — TCP 22

Нужен один чистый клиент-специфичный тест.

Жёсткие ограничения

ТОЛЬКО read-only диагностика.

НЕ:
- устанавливать пакеты
- выполнять apt update/upgrade/install/remove
- перезагружать VPS
- перезапускать Docker
- перезапускать amnezia-awg
- менять UFW/nftables/iptables
- менять маршруты
- менять sysctl
- менять IP/DNS/порты
- редактировать конфиги
- менять VPN-конфигурацию
- удалять/останавливать контейнер
- раскрывать private keys
- раскрывать PSK
- раскрывать пароли
- раскрывать API tokens
- раскрывать root credentials
- печатать полные клиентские VPN-конфиги

Порядок теста

1. Проверь, доступен ли tcpdump.

Если tcpdump установлен — используй его.

Если tcpdump отсутствует:
- НЕ устанавливай его;
- сообщи об этом;
- используй безопасную read-only альтернативу только если она уже доступна;
- если безопасной альтернативы нет — остановись и сообщи пользователю.

2. Подготовь capture ТОЛЬКО для CLIENT_IP=178.178.242.236.

Используй:

timeout 60 tcpdump -ni any "host 178.178.242.236 and ((udp port 32296) or (tcp port 22))" -tttt -nn -vv

Ограничения capture:
- не использовать -X
- не использовать -A
- не выводить payload
- не сохранять pcap на диск без необходимости
- не менять сетевые настройки

3. После запуска capture напиши пользователю ровно:

READY

4. Только после READY пользователь выполнит из ТОЙ ЖЕ российской сети 178.178.242.236:

ТЕСТ A — VPN:
- включить AmneziaWG
- держать попытку подключения 10–15 секунд
- затем отключить

Подождать 5–10 секунд.

ТЕСТ B — SSH:
- выполнить попытку SSH к 206.245.129.65 на TCP 22

5. После завершения пользователь напишет:

Done. Analyze the capture.

6. После этого проанализируй capture.

Что проверить после теста

AmneziaWG:
- были ли входящие UDP-пакеты от 178.178.242.236 на 206.245.129.65:32296
- уходили ли UDP-ответы VPS обратно на 178.178.242.236
- обновился ли latest handshake соответствующего peer
- изменились ли RX/TX transfer counters
- были ли UFW/nftables drops именно для CLIENT_IP

SSH:
- пришёл ли TCP SYN от 178.178.242.236 на TCP 22
- ответил ли VPS SYN-ACK
- дошло ли соединение до sshd
- были ли firewall drops именно для CLIENT_IP

WireGuard:
- можно смотреть latest handshake
- можно смотреть transfer counters
- можно смотреть endpoint peer
- public key только в сокращённом/маскированном виде

НЕ выводить:
- private key
- preshared key
- полный клиентский конфиг

Как классифицировать результат

СЦЕНАРИЙ A
Ни TCP SYN:22, ни UDP:32296 от 178.178.242.236 не пришли.

Вывод:
- проблема находится до VPS
- возможна фильтрация/маршрутизация к публичному IP или подсети
- локальная проблема VPS маловероятна
- НЕ утверждать конкретного виновника без дополнительных доказательств

СЦЕНАРИЙ B
TCP SYN:22 приходит, UDP:32296 не приходит.

Вывод:
- весь IP VPS не заблокирован
- вероятнее фильтрация UDP, конкретного порта или VPN-трафика

СЦЕНАРИЙ C
UDP:32296 приходит, но WireGuard handshake не обновляется.

Вывод:
- сеть до VPS работает
- вероятнее legacy AmneziaWG, сигнатура протокола, несовместимость или клиентская конфигурация

СЦЕНАРИЙ D
Handshake обновляется, но VPN не передаёт пользовательский трафик.

Вывод:
- проверять forwarding, NAT, UFW, return path и transfer counters
- проблема уже после handshake

СЦЕНАРИЙ E
И SSH, и VPN полностью проходят.

Вывод:
- проблема нестабильная или зависит от конкретной сети/момента
- нужен повтор с другой российской сетью или другим оператором

Финальный отчёт

A. CLIENT_IP
- можно замаскировать последнюю октету: 178.178.242.xxx

B. SSH test
- TCP SYN на 22: пришёл / не пришёл
- SYN-ACK от VPS: был / не был
- дошло ли до sshd

C. AmneziaWG test
- UDP на 32296: пришёл / не пришёл
- ответы VPS: были / не были
- handshake: обновился / нет
- transfer counters: изменились / нет

D. Firewall
- были ли drops для CLIENT_IP
- объясняют ли они проблему

E. Локальная причина на VPS
- найдена / не найдена / не доказана

F. Наиболее вероятный уровень проблемы
- фильтрация IP/подсети
- фильтрация UDP
- фильтрация порта
- детект legacy AmneziaWG
- клиентская конфигурация
- серверная маршрутизация/NAT
- недостаточно данных

G. Один следующий шаг, который даст максимум информации.

Если данные укажут на внешний фильтр, только ПРЕДЛОЖИ, но не выполняй:
1. сохранить текущий legacy AmneziaWG как резерв
2. протестировать AmneziaWG 3.1
3. при необходимости запросить новый IPv4 у AdminVPS
4. при смене IP предпочтительно получить адрес из другой подсети
5. перевыпустить новые клиентские конфиги после миграции

Не выполняй изменения без отдельного явного подтверждения пользователя.

Главная задача сейчас: не чинить сервер, а получить чистое доказательство того, доходит ли трафик от конкретного российского IPv4 до VPS по UDP 32296 и TCP 22.
